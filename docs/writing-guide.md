# 教材写作规范

这份规范约束所有面向学生的章节。课程规划、教师备课稿和 API 参考可以使用清单；正式讲义必须像教材，而不是任务管理器。

## 写给谁

默认读者学过 C/C++、数据结构和基础编译原理，但第一次真正使用 LLVM。我们可以要求学生思考，不能要求他们凭空知道 LLVM 的工程惯例。

第一次出现的术语要完成三件事：用朴素语言说明它解决什么问题，给出一个最小例子，再给出正式名称。不要用更多未解释的术语解释一个新术语。

## 一章应当怎样展开

每章从一个具体问题开始。先让学生看到“不学习本章会遇到什么困难”，再引出抽象概念。正文应当有连续的推理，而不是把知识点拆成互不相干的 bullet。

推荐节奏：

1. 用一个可运行或可观察的现象开场；
2. 提出本章要解决的问题；
3. 从最小模型逐步增加一个变量；
4. 在关键处让学生预测结果；
5. 运行工具并解释观察结果；
6. 给出有边界的练习；
7. 用本章建立的模型解释常见错误；
8. 说明下一章为什么自然出现。

学习目标、提交物和验收条件可以保留，但它们不代替正文。

## 示例代码

- 示例必须足够短，使学生能逐行解释；
- 代码出现之前说明要解决的问题，出现之后解释关键行；
- 不贴一大段代码后逐项复述语法；
- 至少展示一次失败及诊断过程；
- 明确哪些细节是课程选择，哪些是 LLVM 规则；
- 未实际验证的命令或代码必须标记，不能暗示已通过测试。

## 练习

练习不是“把 TODO 写完”。每个练习应交代背景、可观察行为、限制、起步提示和完成证据。提示应帮助学生缩小问题，而不是直接泄露答案。

优秀练习至少包含一个需要解释的结果。编译器课程不能只评价程序是否输出 42，还要评价学生能否说明 IR 为什么合法、优化为什么保持语义。

## 语气

使用平静、直接、尊重读者的语言。可以说“先别急着写代码”，也可以承认某个概念第一次看很反直觉。避免宣传语、空泛鼓励、连续反问和模板化总结。

不要把“显然”“简单”“只需”用在学生第一次接触的内容上。对教师熟悉的事情，对学生未必简单。

## 每章完成前的编辑检查

- 开头是否提出了真实问题？
- 新术语是否在首次出现时解释？
- 段落之间是否有因果或递进关系？
- 学生是否知道每条命令应该观察什么？
- 是否区分 LLVM 的结构正确性和源语言语义正确性？
- 练习是否有明确证据证明完成？
- 删除所有列表后，正文是否仍然构成一条完整讲解？
