# 教师组织指南

[简体中文](teaching-guide.md) | [English](teaching-guide.en.md)

## 先固定什么

开课前固定以下变量：

- 一条受支持的 LLVM 主版本线；
- C++ 标准、CMake 最低版本和测试入口；
- MiniLang 语法、类型规则和 runtime ABI；
- Windows/Linux/macOS 的支持矩阵；
- starter code 与 reference solution 的可见性边界。

LLVM API 演进较快。讲义应标注课程版本，不要让学生在多个大版本的博客代码之间拼接。

## Starter code 应提供什么

建议提供：

- 已配置的 CMake targets 和测试命令；
- SourceManager、基础 Diagnostic 数据结构；
- CLI 参数解析骨架；
- 空接口与少量 smoke tests；
- 跨平台构建说明。

建议不提供：

- parser 主循环、类型检查核心规则；
- 控制流 lowering；
- 完整 JIT 封装；
- 能被简单改名提交的参考实现片段。

## 每章交付模板

每个 `chapters/NN-topic/` 最终应包含：

```text
README.md          # 学习目标、概念、步骤和思考题
starter/           # 学生起始代码
tests/             # 公开测试
solutions/         # 教师解答（可拆到私有仓库）
fixtures/          # 输入程序、IR、预期诊断
```

README 的结尾必须写清：提交物、运行命令、验收条件、常见失败模式和拓展问题。

## 控制课程风险

- 第 3 周前确认所有学生能在干净环境构建 LLVM 依赖项目。
- 第 7 周冻结语言规范；之后只修歧义，不新增核心语法。
- 第 9 周提供 runtime ABI conformance test，防止集成期才发现调用约定问题。
- 每个里程碑保留一个“纵向切片”：哪怕功能少，也能从源码走到执行结果。
- reference solution 每周在全部受支持平台跑 CI。
- 为机器配置较弱的学生提供预构建 LLVM 或容器方案，但仍要求理解工具链。
- MLIR、GPU 与 Transform dialect 独立成选修层；核心课程不得依赖特定 GPU。
- MLIR 作业固定到与 LLVM 相同的发布线，并保存每一层 IR fixture，降低 API 演进带来的维护成本。

## 推荐的反馈方式

代码评审优先检查：

1. 错误路径是否安全；
2. 模块边界是否被绕过；
3. 测试是否证明语义而非实现细节；
4. IR 是否满足类型、终结指令、支配关系与 ABI；
5. 学生能否解释设计，而非仅称“参考资料就是这样写的”。

## 学术诚信设计

最终项目天然容易复制公开教程。可通过以下方式提高原创思考含量：

- 让学生提交决策记录与失败实验；
- 为不同小组分配小型语义变体，但保持相同难度；
- 答辩时现场修改一条语言规则并定位受影响模块；
- 测试隐藏边界行为，不隐藏核心规范；
- 评价解释、测试和演进过程，而不只评价最终代码。

## 前沿内容的教学边界

前沿不等于罗列名词。一个专题只有同时具备以下条件才进入动手主线：

- 学生能在两周内构造最小闭环；
- 有确定的 verifier、测试或性能指标；
- 能解释它解决了基础架构中的什么限制；
- 不依赖稀缺硬件也能完成核心验收。

CIR、量化、稀疏张量、自动微分、e-graph、专用加速器后端等更适合作为论文阅读或课程项目选题；只有 MLIR 基础、自定义 dialect 与 dialect conversion 建议形成连续实验。
