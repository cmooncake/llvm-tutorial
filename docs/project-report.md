# 研究项目报告与实验记录

[简体中文](project-report.md) | [English](project-report.en.md)

最终报告回答一个具体问题，不是按日期列出实现过程。正文建议 6–8 页，附录保存长 IR、完整命令和原始数据。负结果可以是有效结论；关键是读者能判断结果支持什么、不支持什么。

## 提案

M1 使用 1–2 页回答：你要验证什么假设，基线是什么，最小实现在哪里改变编译器，怎样发现语义错误，以及什么结果会让你放弃原假设。列出两周内能运行的切片和一个不依赖 GPU/外部服务的退路。

例题：“对四类小循环，保守的范围分析能否减少动态边界检查，而不改变 trap 行为？”这是可测问题。“实现一个很强的优化器”不是。项目范围冻结后，新增语言特性要说明它是否服务于原问题，否则放入后续工作。

## 方法与正确性

说明源语言规则、分析域、转移函数、收敛策略和变换前置条件。若是 MLIR 项目，写出每阶段的合法 operation、类型转换、materialization 和仍未 lower 的部分。区分实现中的保守近似与语言语义。

给出至少一个必须变换、一个允许但不必变换、一个禁止变换的输入。描述 oracle 的独立性：两条路径共用前端时，它们不能发现同一个前端错误。有限随机测试、verifier 和形式化验证各有覆盖边界，不能用其中一个名词替代论证。

## 评估方案

至少包含三个可解释的工作负载和一类预计不会受益的输入；若资源有限，可减少数据规模，但不能只保留最快的样例。记录输入来源、随机种子、数据规模、编译参数、commit、SDK 版本、CPU、系统和测量日期。

先验证结果再计时。分开测量编译/优化、进程启动或 JIT、steady-state kernel。每个配置至少进行 3 次预热和 20 次正式运行，交替或随机化配置顺序；若耗时极长，可减少次数并解释不确定性。记录所有有效样本，不因样本较慢就删除。报告中位数与离散程度，以及每个 workload 的退化。

速度比定义为同一 workload 的基线时间除以候选时间，大于 1 表示候选更快。跨 workload 汇总时可使用这些比值的几何平均，但不能把不同量纲的绝对耗时混合平均。数据量少或噪声较大时，报告观察结果与限制，不宣称统计显著。

至少做一项消融：关掉你的 Pass、移除一个分析条件、关闭一项 schedule，或对照恒定保守策略。不得为了消融放开错误变换后仍将结果纳入性能平均。正确性失败的数据单独列出，并说明失效原因。

## 报告顺序

仓库提供 `tools/measure.py` 作为确定性可执行程序的计时起点：

```sh
python3 tools/measure.py --baseline build/base --candidate build/candidate \
  --arg=100000 --runs 20 --warmups 3 \
  --context "commit=<sha>; LLVM=22.1.8; flags=<flags>; workload=<name>" \
  --output build/timing.json
```

工具每次核对 stdout/stderr，任何失败或不一致都中止；保存命令、二进制摘要和全部样本。这是含进程启动的端到端计时，不是 kernel-only 或 JIT steady-state 基准。计时数据不能代替语言正确性测试。

1. 问题、假设与贡献：一段话说明与已有基础设施的区别。
2. 语义与方法：前置条件、实现边界、正确性论证。
3. 实验设置：基线、工作负载、环境、指标与统计方法。
4. 结果：逐项结果、消融、负结果与解释。
5. 有效性威胁：共同前端、规模、目标机、缓存、编译器版本等限制。
6. 结论与可复现信息：只总结实际证据支持的主张。

附录放构建/运行命令、测试日志、原始 JSON/文本数据、依赖版本、引用与个人贡献。不要只交图或最快的数字。第三方复现者应能判断“构建失败”“运行错误”“性能不同”分别发生在哪里。

## 答辩与同行复现

每组展示 15 分钟、质询 10 分钟。演示包括一个正例、一个反例、一层中间 IR 和一张有基线的结果图；不以现场跑完整 benchmark 耗尽时间。教师随机请每位学生解释一个跨模块边界。

另一组按原始命令复现一个结论，并记录环境差异、失败步骤和所需帮助。作者在最终报告中回应。复现失败首先是可观察的工程事实，不能立即归因于复现者“不熟悉环境”。
