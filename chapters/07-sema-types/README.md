# 第 07 章：静态语义与类型检查

[简体中文](README.md) | [English](README.en.md)

> 预计用时：7–10 小时。先修：第 06 章与 MiniLang 类型规则。

通过 parser 只说明程序具有合法语法。`x + true` 可以形成完好的二元表达式节点，却不符合 MiniLang 类型规则；`answer()` 可以形成调用节点，却可能没有任何函数声明。静态语义阶段负责这些不能仅靠语法回答的问题。

## 7.1 分阶段处理

推荐把名字解析与类型检查分开。第一遍收集顶层函数签名，使函数可以调用文本位置靠后的函数；随后进入函数体，按词法作用域解析参数和局部绑定；最后在已解析的引用上检查表达式与控制流类型。

不要使用 LLVM Type 作为前端类型系统。MiniLang 的 `bool`、`unit`、数组值语义和错误类型都有源语言含义；它们以后可能以多种 LLVM 类型或 runtime 约定实现。

## 7.2 作用域与名字解析

作用域可以实现为栈，每层保存本层声明。进入块时 push，离开时 pop；查找从内向外进行。重复定义只检查当前层，遮蔽则发生在不同层。

初始化表达式在新名字进入作用域之前检查，因此 `let x = x;` 引用的是外层 `x`，没有外层定义时报告 `E2001`。`var`、`let`、参数和函数符号应有不同类别，以便赋值检查产生准确诊断。

解析成功后，名字表达式应指向稳定的声明标识或符号，不应在 codegen 时再次按字符串猜测绑定。

## 7.3 类型检查

类型检查函数应返回类型或错误类型。错误类型用于抑制级联诊断：`unknown + true` 已经因 `unknown` 未定义而失败，不应再无意义地报告多个运算符类型错误。

对每个运算符和语言结构写出局部规则。例如 `+` 要求两个 `i32` 并产生 `i32`；`<` 要求两个 `i32` 并产生 `bool`；`if` 条件必须是 `bool`，有 `else` 时两分支类型一致。

函数返回检查不仅查看显式 `return`，还要分析可达路径。课程基础版可以实现保守的 definitely-returns 分析：如果不能证明所有路径返回，就为非 `unit` 函数报告 `E3003`。

## 7.4 诊断是接口

每条诊断包含稳定编号、主源码范围和结构化参数；自然语言文本可以改善，但测试主要断言编号、关键参数和范围。类型不匹配时同时指出实际类型和期望类型，必要时用 secondary span 指向原声明。

诊断阶段不得因前面产生错误节点而崩溃。错误恢复不是 parser 独有的问题，整个前端都要能够在局部失败后继续处理安全的部分。

## 实验 7：Resolver 与 Type Checker

实现：

- 顶层函数签名收集与重复定义检查；
- 块作用域、遮蔽、未定义名字与可变性；
- 所有 MiniLang 1.0 表达式的类型规则；
- 调用参数数量和类型检查；
- 条件类型、分支统一与缺失返回；
- typed AST dump 或独立的语义标注输出。

测试应按诊断类别组织，每类至少包含一个成功、一个直接失败和一个用于抑制级联错误的案例。

### 设计题

考虑：

```text
let x = 1;
{
  let x = x + 1;
}
```

解释内层初始化式中的两个 `x` 分别如何解析，以及为什么“声明何时进入作用域”必须成为语言规范，而不能由符号表实现偶然决定。

## 小结

静态语义把“语法上像程序”的 AST 转换为引用明确、类型一致的程序表示。第 08 章的 codegen 只接收通过静态语义的输入，因此不需要一边生成 IR 一边猜测源语言错误。
